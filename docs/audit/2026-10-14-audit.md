# cmdit code audit — 2026-10-14 (1.3.2)

> A full sweep of `src/cmdit.cyr` at 1.3.1, the first since the 1.2.4 P-1 audit. The priority
> was the code added since then, which had not been reviewed adversarially: 1.3.0's
> word-at-a-time zeroing and single-walk argv, and 1.3.1's growth paths, `CMDIT_ERR_NOMEM`
> and `=value` rejection. Same question as [the 1.0.0 audit](2026-06-25-audit.md): can argv,
> env or program misuse drive an out-of-bounds access, an overflow, a NULL dereference, or a
> result that contradicts the documented contract?

**Result:** two attacker-reachable defects, both fixed in 1.3.2:

- **SEC-6:** a residual of the 1.2.4 completion-injection fix, where a leading `-` in an
  attacker-chosen `argv[0]` became options to bash's `complete`.
- **SEC-7:** a command line too long to read whole (or unreadable) silently parsed as a prefix.

No attacker-reachable memory-safety defect was found. The memory defects (SEC-8 to SEC-10) all
need program misuse first. Eight contract defects in verb dispatch, completions and the repeat
view are fixed too. **Every fix is mutation-proven:** reverted in a scratch copy, the suite
fails, crashes or hangs. The exceptions are the two items marked *unproven*, which no fixture
can reach.

## Method

Three independent finders, each with one lens, plus a full manual read of the file:

- **A**, memory safety and integer arithmetic;
- **B**, contract and state consistency against the README, ADRs, doc comments and CHANGELOG;
- **C**, the output surface: renderers, `cmdit_print_error`, and the three completion emitters.

Each finder had to back a claim with a reproducer or an exact line trace. Each claim was then
re-verified against the code before it counted. Behavioural findings were first written as
tests and shown to **fail** on the unfixed code, then fixed. Results: **503/503** assertions,
33/33 seeded reverts caught, `cyrius fuzz --poison=ab` and the whole suite under
`CYRIUS_POISON=1` clean, `cyrius audit` clean on every stage, and the bundle passing the full
suite on a 6.6.2 compiler.

## Threat model

Unchanged from [2026-06-25](2026-06-25-audit.md#threat-model):

- **Attacker-controlled:** the argv vector (including `argv[0]`, which becomes the program name
  on the `cmdit_new(0)` path) and any env var bound with `cmdit_env`.
- **Program-controlled:** indices, registered names, choice sets, help strings, and the `argc`
  a caller hands to the pure cores.
- **Robustness:** program misuse is not an attacker primitive, but it is in scope. A library
  that documents "returns 0 on OOM" has to survive that 0.

### SEC-6 — a leading `-` in the program name became `complete` options (Medium, attacker-reachable) — FIXED

**The 1.2.4 fix and its gap.** 1.2.4 routed the program name through
`_cmdit_oprint_cmdname`, which maps every byte outside `[A-Za-z0-9_.-]` to `_`. Its comment
argued that `-` "is not a shell metacharacter in command-word position". That holds mid-word.
It does not hold for the **first** byte of the name argument to bash's `complete`, fish's
`complete -c` or zsh's `#compdef`, where the shell reads a leading-dash token as options. On
the documented `cmdit_new(0)` path, the name is `argv[0]`, which is chosen by whoever execs the
tool.

**Verified on 1.3.1** (finder C, reproduced end to end):

- `argv[0] = "-DCtrue"` generated `complete -F __DCtrue_complete -DCtrue`, a script that passes
  `bash -n`.
- Merely sourcing it in a clean `bash --norc` left `complete -p -D` printing
  `complete -C 'true' -F __DCtrue_complete -D`. The user's **default** completion was replaced,
  and bash runs the PATH command `true` on every TAB for any command without its own
  completion.

The payload is constrained by the surviving alphabet to one bare command name, with no
arguments, no `/` and no `;`. That makes it strictly weaker than the arbitrary multi-line code
of the 1.2.4 bug. But it has the same attacker, the same sink (a script whose purpose is to be
sourced), and lands at the same place in the user's shell. `-r` (remove completions), `-E` and
`-I` hijack completion state without any command at all.

**Fix:** `_cmdit_oprint_cmdname` also maps a **leading** `-` to `_`. One place, all three
shells. Real program names never start with `-`, and internal dashes (`cmdit-smoke`) are kept.
**Tests:** `-DCtrue` reaches no emitter unmapped, in bash, fish or zsh, and `tool-x` keeps its
dash.

### SEC-7 — a command line too long or impossible to read whole parsed as a prefix (Low, attacker-reachable) — FIXED

`cmdit_parse` / `cmdit_dispatch` build argv through stdlib `args_init`. On Linux, that reads
`/proc/self/cmdline` **once** into a fixed 2 MiB buffer.

- **Too long.** ARG_MAX rises with an unprivileged `ulimit -s unlimited` (6 MiB on the audit
  host). Every whole token past 2 MiB was silently dropped, and the parse returned `CMDIT_OK`.
  A caller who pads `"$@"` can strip a restricting flag that a wrapper appends after it
  (`exec tool "$@" --read-only`). **Verified on 1.3.1:** 30 arguments of 100,000 bytes followed
  by `--loud` gave exit 0, `loud = 0` and 20 positionals.
- **Unreadable.** With no `/proc` mounted (early boot, a bare chroot), or when `args_init`'s
  own alloc failed, `argc()` is 0. cmdit then parsed an empty argv and ran ignoring every flag
  it was given. On Linux ≥ 5.18, an exec'd program always has an `argv[0]`, so `argc() == 0`
  means the command line could not be read.

**Fix:** a new append-only code, **`CMDIT_ERR_ARGV = 13`** ("could not read the full command
line"). `cmdit_argv` sets it, and `cmdit_parse` / `cmdit_dispatch` return `CMDIT_RESULT_ERR`
instead of parsing a prefix, when:

- the count is ≤ 0, or
- `args_init`'s single read filled its 2 MiB buffer (`_args_len`, Linux only).

Memory safety was never at stake here: `argc()` counts only NUL-terminated strings, so a
partly read last token is dropped whole.

**Tests and verification:**

- `_cmdit_argv_whole`, the pure predicate behind the check, is unit-tested.
- The exact scenario above now exits 2 with the new message, on both the 6.7.9 and the 6.6.2
  compiler.

⚠ **The truncation itself is in the stdlib**, and every user of stdlib `args` sees it. It is
filed against cyrius as cyrius `docs/development/issues/2026-10-14-args-init-truncates-argv-past-2-mib.md`. cmdit's check is a consumer-side refusal and does
not change what `args_init` returns.

**Update (1.4.2, 2026-10-28).** cyrius 6.7.12 resolved the issue (now under
`docs/development/issues/archived/`): `args_init` reads to EOF. A pre-6.7.12 read never
returns more than 2 MiB, so cmdit now refuses only a read of exactly 2 MiB, the one length
that may be a cut. Built against the 6.7.9 stdlib, 1.4.2 refuses exactly what 1.3.2 refused.
Built on 6.7.18, the scenario above exits 0 with `loud = 1` and all 30 positionals.

### SEC-8 — slot-count byte sizes wrapped to small buffers (Low, program misuse) — FIXED

Three places turn a count of pointer slots into an `alloc` size with `* 8`:

- the 1.3.1 growth (`_cmdit_grow`);
- the dispatcher's remainder array, `(argc + 1) * 8`;
- `cmdit_argv`'s array.

Past 2^60 slots, the multiplication wraps, and it can wrap to a size `alloc` grants:

- `argc = 2^61` gave an 8-byte remainder that the dispatch loop then wrote past;
- a positional capacity of 2^61 + 1 doubled to a 16-byte request, and `_cmdit_grow` copied
  ~2^61 slots out of it.

1.2.4 clamped a negative `argc` and never considered an overflow-large one. 1.3.1's own NOMEM
test used 2^59, whose size happens to wrap negative, so it passed by luck. This audit's suite
found the bug when a test drove the repeat path to 2^62 + 1 and the binary died with SIGSEGV.

**Fix:** one bound, `_CMDIT_SLOTS_MAX = 2^60 − 1`, enforced wherever a slot count becomes a
size. `_cmdit_grow` also refuses a capacity below its copy count. **Tests** cover both exact
wrap values.

### SEC-9 — the public layout vars were read live (Low, program misuse) — FIXED

`CMDIT_FLAGS_MAX`, `CMDIT_POS_MAX`, `CMDIT_REPEAT_MAX`, `CMDIT_VERB_MAX`, `CMDIT_ENTRY_SIZE`,
`CMDIT_VERB_SIZE` and `CMDIT_CTX_SIZE` are mutable `var`s, and the code read them at use time.
Finder A proved each consequence under the poisoning allocator:

- raising a cap after a table was allocated overflowed the heap (exit 86);
- a 2^61 + 1 cap wrapped its allocation;
- setting `CMDIT_REPEAT_MAX = 0` hung the next repeat push;
- `CMDIT_FLAGS_MAX < 2` left the `--version` index at -1, and `cmdit_version_short` then wrote
  112 bytes before the entry table.

ADR-0003 already called them internal, not API.

**Fix:** the model stdlib 6.7.9 adopted for its own public bound vars. The layout lives in a
private `enum CmditLayout`, which Cyrius will not let a program assign. The code sizes and
strides only from it, or from the cap each handle stores. The public vars keep their values
for readers and are now **read-only in effect**. **Tests** mutate four of them mid-run and show
that registration, repeat pushes and entry strides are unaffected.

### SEC-10 — `cmdit_verb_alias` accepted any id (Low, program-created state) — FIXED

Only `verb_id < 0` was rejected. An alias of a missing id dispatched to a `cmdit_verb_matched`
value nobody registered. Its target row was then read by the dispatcher, `cmdit_parse_verb` and
`cmdit_verb_help_at`:

- ids below 128 read zeroed rows;
- ids of 128 or more read **outside** the verb table. Finder A leaked a neighbouring heap
  string through `cmdit_verb_help_at`, and crashed the dispatch at 2^44, from an
  attacker-supplied token that named the alias.

An id equal to the alias's own row made it render as a real verb. **Fix:** the target must be a
registered, canonical verb. **Tests** cover both rejected cases.

### SEC-11 — a 0 handle crashed most of the API (Low, program misuse) — FIXED

1.2.4 made `cmdit_new` return 0 when `alloc` refuses, and said "every public entry point
tolerates a 0 handle". Only the getters and modifiers did. Registration, the whole parse
family, the positional, error and verb-slice accessors, the renderers and `cmdit_print_error`
all dereferenced address 0. A caller that did not check `cmdit_new` (none of the demos do)
crashed in its first `cmdit_bool`.

**Fix:** every public entry point guards the handle, and the guards **fail closed**. A 0
handle only ever comes from `cmdit_new`'s OOM, so:

- registration returns -1;
- the parse family returns `CMDIT_RESULT_ERR`;
- `cmdit_error(0)` is `CMDIT_ERR_NOMEM`, and `cmdit_print_error(0)` prints "out of memory".

**Tests:** one assertion per entry point.

### SEC-12 — zsh and fish skipped the 1.2.1 whitelist (Low, program-supplied) — FIXED

1.2.1 said names "are now whitelist-filtered … and dropped if they fail", but only the bash
emitter did it.

- **fish** stores a `complete -a` argument and expands command substitutions in it on every
  completion; that is how its documented `-a "(cat /etc/passwd | cut -d : -f 1)"` example
  works. A verb named `x(touch /tmp/p)` would run at TAB time inside correct single quotes.
- **zsh:** a `:` in a name split `_describe`'s pair.

Verb names are program-supplied, so no consumer was exposed. **Fix:** both emitters apply
`_cmdit_name_is_safe`. (The fish half is established from fish's documented behaviour; fish
is not installed on the audit host.)

### SEC-13 — two OOM paths reported nothing, or parsed nothing (Low) — FIXED, one unproven

- **The dispatcher.** Its refused remainder alloc returned `CMDIT_RESULT_ERR` with
  `cmdit_error` still NONE. It was the only error path that set no code, so
  `cmdit_print_error` printed "argument error". It now sets `CMDIT_ERR_NOMEM`. The test uses
  `argc = 2^28`, a valid size just past stdlib `ALLOC_MAX` (2 GiB).
- **`cmdit_argv`.** A refused array alloc returned 0, and `cmdit_parse` then parsed an empty
  argv, a fail-open on OOM. It now reports NOMEM through the same path as SEC-7. ⚠
  **Unproven:** no fixture can make the process's own small argv fail to allocate.

### SEC-14 — `_cmdit_repeat_cap` could loop forever (Info) — FIXED

Past 2^62, a doubling of the derived repeat capacity wraps negative, then to 0, forever. This
is unreachable from argv. **Fix:** past 2^62 it returns the count, and SEC-8's bound refuses
the grow (NOMEM). With the guard reverted, the suite hangs and is killed by a 60 s timeout.

### COR-1 — a trailing-marked verb counted its own flags (Medium) — FIXED

Every token passed to a `cmdit_verb_trailing_after` verb counted toward its threshold,
including verb-scoped flags. In `exec --tty --root /x c1 ls`, `--tty` met exec's one
positional, the global `--root` fell into the payload, and the verb scope failed with UNKNOWN.
That broke "globals before or after the verb" for exactly the verbs (stiva `exec`) that most
need flags.

**Fix:** only non-flag tokens count. A verb flag's separate value (`-w /app`) still counts,
which can only start the payload earlier than the verb's own parse does. A global inside the
payload is still never applied, and a test pins that.

### COR-2 — `tool add --help` was blocked by a required global (Medium) — FIXED

The dispatcher hands an after-verb `--help` to the verb, but `cmdit_dispatch` still ran the
global required check, so the user got "required flag missing". README promises that
`tool add --help` shows the subcommand's help. **Fix:** a new ctx slot, `+168 help_deferred`
(ctx 168 → 176 B, append-only), is set when an auto `--help` / `--version` is deferred, and
`cmdit_finalize` then skips the required check. The env fallback still runs.

### COR-3 — `--` at a trailing threshold reached the payload (Low) — FIXED

On a marked verb, `exec c1 -- ls -l` (1.2.2's documented escape hatch) ran the command `--`.
**Fix:** a `--` exactly at the threshold is consumed, kubectl-style, and a second `--` is data.
This is a visible change for anyone who passed a literal leading `--` to a marked verb.

### COR-4 — a bundled short before the verb was UNKNOWN (Low) — FIXED

`t -vx add` and `t -ofile add` (with `-o` registered) reported UNKNOWN, where
`cmdit_parse_argv` says BUNDLED. The two cores now agree.

### COR-5 — trailing marks on alias rows did nothing (Low) — FIXED

`cmdit_verb_trailing_after(h, alias_row, n)` returned success but stored the mark where the
dispatcher never reads it. `cmdit_verb_trailing_at(h, alias_row)` read -1 even when the verb
was marked. Both now resolve through the alias.

### COR-6 — completions did not skip a short value flag's argument (Low) — FIXED

The completion skip set listed only `--long` spellings. In `tool -j 5 <TAB>` (or `-r /x`), the
value was taken for the verb and files were offered. This is the short-flag twin of the bug
1.2.1 fixed. **Fix:** both spellings are emitted, for bash and zsh.

### COR-7 / COR-8 (Info) — FIXED

- **COR-7:** an empty (non-null) program name emitted `complete -F __complete ` with no name.
  It now falls back to `prog`, as a null name always did.
- **COR-8:** `_cmdit_repeat_push` set the last-wins value before its alloc could fail. An env
  fallback whose push was refused therefore still changed `cmdit_get_str`, against the
  "env failure leaves the default" contract. The value is now written only after a successful
  push.

### PERF-1 / PERF-2 (Info) — FIXED

- **PERF-1.** 1.3.0 moved `cmdit_new`'s entry-table zero to `store64`, but the first
  `cmdit_verb` zeroes a second, 4096-byte table that was still `store8`. Handle + first verb:
  **8.36 → 2.83 µs**, paid on every run of every verb tool. A new `verb_new_floor` bench tracks
  it. ⚠ It cannot be observed by a test, because fresh `alloc` memory is already zero.
- **PERF-2.** `cmdit_argv` cached the argv per *handle*, so each handle that called
  `cmdit_parse` re-ran `args_init` and its never-freed 2 MiB buffer. The argv is now
  materialized once per process and shared.

### DOC-1 — stale claims (Info) — FIXED

- **Source comments:**
  - the header called the error codes byte-compatible with stdlib `FlagErr` (only 0..4 are);
  - the supported-syntax block predated 1.3.1's `=value` rule;
  - the NOT-supported list omitted optional-value flags, float flags and `-x=value`;
  - the trailing slot was documented as "-1 = off" (it is 0);
  - the context layout said 160 B and omitted `+160`;
  - the verb row's `+24` was called "reserved";
  - the bench harness described the pre-1.0 6656-byte entry table.
- **Elsewhere:**
  - README said `cmdit_parse` "short-circuits" to `CMDIT_HELP`; the whole argv is still
    scanned, and an error anywhere wins;
  - `cmdit_completions` said it completes "verbs and flags", but zsh and fish complete verbs
    only;
  - ADR-0002 now records the `+24` slot and the mirror case below.

## Accepted / documented (not changed)

- **A verb value flag whose separate value spells a global flag gives the global**
  (`tool add --name --verbose`). This is inherent to one-pass dispatch, because the dispatcher
  cannot know a verb flag's arity. It mirrors the "global value flag swallows the verb" case
  ADR-0002 already records. Now documented in README and ADR-0002; `--name=--verbose` is
  unambiguous.
- **`--` before the verb ends global flags only, and help-letter remapping is per handle.**
  Both are deliberate and now documented in README.
- **`cmdit_print_error` echoes raw `argv[0]` and an unknown-verb token to stderr.** That is a
  terminal, not a sourced script; it is common CLI practice and accepted.
- **Degenerate program-supplied names** (an empty long name, a flag with neither name) render
  odd but harmless help rows; completions drop them.
- **Short or failed writes are ignored by the renderers.** This is the stdlib norm, for a few
  KB to a pipe or file.
- **Windows `getenv` returns 0 for an empty variable**, so "a set-but-empty env var turns a
  bool on" holds on Linux but not on Windows.

## Conclusion

1.3.2 closes the residual of the 1.2.4 security fix (SEC-6) and the argv-bridge fail-open
(SEC-7). These were the two defects an attacker could reach. The 0-handle tolerance and the
name whitelist had been claimed more widely than implemented; both claims are now true and
tested. The 1.3.0 / 1.3.1 code held up except for SEC-8's size wrap, which the old NOMEM test
had masked. Every fix is mutation-proven, except SEC-13's `cmdit_argv` OOM branch and PERF-1,
which no fixture can reach.
